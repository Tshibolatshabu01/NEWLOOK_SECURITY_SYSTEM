# NEWLOOK SaaS V12.3 — Deep Service Migration

## Objective
V12.3 continues the V10-preserving rebuild without replacing the existing Admin or Payroll applications. Existing DOM IDs, workflows, payroll engines, and collection names remain intact.

## Changes
- Admin tenant collection/document access in `Js/admin.js` is routed through `SaaS/apps/admin/service.js`.
- Guard tenant collection/document access in `Js/guard.js` is routed through `SaaS/apps/guard/service.js`.
- Attendance tenant collection/document access in `Js/attendance.js` is routed through `SaaS/apps/attendance/service.js`.
- Payroll tenant collection/document access in `Js/payroll.js` is routed through `SaaS/apps/payroll/service.js`.
- The service facades accept the legacy V10 Firebase reference call shapes so business logic does not need a destructive rewrite.
- Every service reference acquisition first validates the active tenant with `assertTenant(getCompanyId())`.
- Security Guard remains bound to `shiftRecords`; Staff Attendance remains bound to `attendanceRecords`.

## Preservation rule
This is an incremental migration. The original V10 applications remain the functional source of truth. No simplified replacement application was introduced.

## Next stage
Continue migrating high-risk write workflows behind domain services in small behavior-preserving slices, then perform Super Admin boundary migration and full static/security regression checks.
